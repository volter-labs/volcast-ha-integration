# v2.0.0-beta7 — onboarding and control

This is a **pre-release** building on v2.0.0b6. The new brands below are read-only, and, where the matching Volcast cloud feature is enabled for your account, the control switch follows the consent you give in the Volcast app (see below).

## What's New

### Reading input registers

- The Modbus core can now read input registers (function code 4), not only holding registers. Brands that report their measurements on input registers can be read directly.
- GoodWe and Deye are unchanged.

### Eight draft brand profiles

Each profile is marked **draft**. They are available for the read-only test connection (**Installation details → Read-only test connection**), and their `ha` entries are only hints for mapping the readings of an existing integration: the integration's control through Home Assistant entities (entity mode) is not offered for any of them until that integration entry is verified, and the cloud is told that no setting can be controlled. When several profiles describe the same integration (`solarman`, `solax_modbus`), the device's manufacturer and model text decides between them; if it does not, no profile is selected and the discovery sensor lists the candidates in `profile_candidates`:

- Huawei SUN2000 (L1/M1, through an SDongle over Modbus TCP) — `huawei-sun2000`
- Sungrow SH (WiNet-S, Modbus TCP) — `sungrow-sh`
- SolaX X1/X3-Hybrid G3/G4 (Modbus TCP or RTU) — `solax-x-hybrid`
- Sofar HYD 5-20KTL-3PH (Solarman logger or RTU) — `sofar-hyd`
- Solis hybrid S5/S6-EH1P and RHI (Solarman stick or RTU) — `solis-hybrid`
- FoxESS H1-G2/AC1-G2/P1 (RS485 gateway; readings through `foxess_modbus` only) — `foxess-h`
- SolarEdge StorEdge and Home Hub (Modbus TCP, port 1502) — `solaredge-storedge`
- Fronius GEN24 (Modbus TCP) — `fronius-gen24`

### Documentation for contributors

- `docs/profiles/authoring.md` — a guide for writing a brand profile.
- `docs/profiles/engine-gaps.md` — the vendor control features that the profile schema and the control engines cannot express yet, with the brands they affect and what the core would need.

## Inverter control onboarding

- After discovery, **Options → Inverter control** recommends a control path: through the inverter integration's entities, directly over the local network, or off. The recommendation follows what the inverter integration offers (write, read-only or nothing) and whether the inverter was identified.
- **Options → Inverter control → Choose inverter entities manually** opens an entity map where each inverter setting (mode, power limits, state of charge, export limit, battery and grid readings) can point at a specific entity. A field left as suggested keeps the automatic match.
- Automatic per-device verification: before the first write to an inverter, Volcast climbs a ladder. It starts with a read-only trial that only counts the writes it would have made, then a control write confirmed by read-back, and, where the profile supports it, a short test window. A profile already marked verified skips the trial and starts at the control write. A stop returns the inverter to the settings it had before Volcast took control. A repair notice offers a retry from the step where verification stopped.
- Competing controllers are detected. If another controller writes the same inverter settings, a repair asks you to choose who controls the inverter: Volcast, or your own controller, in which case Volcast only plans (plan-only mode).
- A verification sensor shows the current state of the device verification.

## Changes since v2.0.0b6

### Pairing, onboarding and version check

- Pairing again no longer gets stuck when a new pairing session starts.
- A clearer version check: an outdated client is refused at pairing with a message, and an available update is flagged.
- The first plan is requested again once inverter readings arrive, so a late start does not leave the plan empty.
- The price and consumption steps are taken from the state of your account.

### Where readings come from

- Diagnostics show where each reading comes from.
- A repair notice appears when no inverter readings arrive.

### Choosing how Volcast controls the inverter

- **Options → Inverter control** explains entity control and direct control, and recommends one of them.
- The manual entity map explains each setting, its expected unit and sign, and typical entity names. A preview step shows the converted values and warnings before you save.
- An entity that reports a unit Volcast cannot use is reported instead of being accepted.

### GoodWe ET energy counters and battery limits

- The GoodWe ET profile now also reads the house load energy (total and today), the battery charge and discharge energy totals, and the battery management's charge and discharge current limits. These registers were checked on a GW8KN-ET. The house load energy for today is not yet confirmed on hardware: compare it with the inverter display before relying on it.
- Battery power limits are reported only from a sample taken where the battery management does not throttle them. Otherwise the limits are left out, so the cloud keeps the configured power. 

### Control switch and account consent

- When the matching Volcast cloud feature is enabled for your account, the Volcast control switch in Home Assistant follows the consent given in the Volcast app. Turning it on needs that consent; if it is missing, a repair notice explains why the switch stays off.
- Without the cloud feature, the switch behaves exactly as in the previous beta.

## Direct control stays disabled for the new brands

Nothing is written to the inverters of the eight brands above. Control for any of them needs a live verification on the inverter first, and until then only the read-only test connection is available.

## Known Limitations

- SunSpec scale factors are fixed assumptions in the draft Fronius and SolarEdge profiles; an inverter that reports under another scale factor shows values that are off by a factor of 10 or more.
- Some brands (FoxESS) have no serial or rating register, so they cannot be identified on the direct path; until the `foxess_modbus` integration entry is verified they get readings only, no control.
- A pending switch-off can be lost on any entry reload (an options save, a restart). The failure is safe: Home Assistant stays off while account consent stays on, and the next switch or app action resolves it.
- The known limitations of v2.0.0b6 still apply.

## Upgrading

Update via HACS and restart Home Assistant. Installing or updating does not start any writes to the inverter. Writes need both the consent in the Volcast app and the control switch in Home Assistant; another holder of the same API key can also restore the switch. Where the account-consent mirror is enabled (see above), these two are kept in step: turning the switch off in either place turns it off everywhere, and turning it on in Home Assistant only restores a consent that was already given in the app.
