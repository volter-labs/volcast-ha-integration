# v2.0.0-beta11 — PV first while charging from grid, one production source

This is a **pre-release** building on v2.0.0-beta10. The PV-first change applies only while a grid-charge slot of the plan is active; the other changes in this release are described below.

## What's New

### PV first during grid charging

- While a grid-charge slot is active and PV production covers the planned charging power, the battery takes the solar surplus (solar production minus household consumption) instead of the inverter holding a fixed grid-charge power and exporting the surplus.
- If the surplus drops, planned grid charging resumes.
- Applies to inverters whose profile charges from the grid at a fixed power. Currently this is the GoodWe ET family.

### Damped switching and write budget

- Switching is damped: about 3 minutes of sustained surplus are required to switch to PV-first charging, and about 5 minutes with the surplus clearly below the planned power (more than 200 W below) to switch back.
- Switching into PV-first charging uses at most half of the daily mode-write budget of the inverter, leaving the rest for the plan. Staying in PV-first charging and switching back are never blocked by this limit.
- It is never active during the device verification test window.

### One production source per account

- When inverter control's telemetry reports PV power (`pv_power_w`: from the profile registers in direct mode, from the mapped profile entities in entity mode, or from the manual telemetry map), Volcast calibrates the forecast on the server from that telemetry. The integration's own production tracker, daily reconciler, submit queue, reconciliation diagnostic entities and sync button are not started in this case. A PV energy counter alone does not count.
- Entries without inverter control, and paired entries whose telemetry carries no PV power (for example a read-only profile match without mapped entities), keep the tracker fed from the mapped PV energy or power sensors, as before.
- The "production tracking available" repair notice now appears only when there is no source at all (no mapped sensor and no telemetry production). Its text explains the telemetry option.
- A new repair notice, "PV sensors are no longer used for calibration" (warning, not fixable), appears when telemetry from inverter control reports PV power and PV sensors are still mapped. Clearing the sensors in the Forecast options removes it.
- Turning inverter control on (from off to direct or entity mode) in the options shows an information step, "Forecast calibration now uses inverter telemetry", that names the mapped sensors. It has a single continue button.

### Forecast entities keep their last values when a refresh fails

- When a forecast refresh fails after retries, the forecast entities keep their last values instead of becoming unavailable. Before, this blanked the Energy Dashboard.
- `integration_healthy` still reports the failure. The entities are unavailable only when no data was ever loaded.

### New diagnostic sensor `sensor.volcast_forecast_age`

- Shows the minutes since the server generated the forecast, updated every minute.
- Attributes: `generated_at`, `server_reported_cache_age_minutes`, `minutes_since_last_success`, `consecutive_failures`.

### API status shows the server-side calibration

- The API status sensor now shows the calibration that the server applies: attributes `production_source`, `production_source_detail`, `kalman_bias`, `kalman_updated_at`, `calibration_buckets` and `last_production_hour`. The values are provided by the server; they are empty (null) when the server provides no calibration.
- It no longer shows the local tracker's calibration.

### Visibility

- The control telemetry shows when PV-first charging is used, as a `pv_first` note in the decision.

### Internal

- Battery power is now part of the live telemetry used by the control cycle.

## Upgrading

Update via HACS and restart Home Assistant.

### After updating

If you had PV sensors mapped and inverter control now reports PV power through telemetry, the submit queue depth sensor, the last reconciliation sensor and the sync button are no longer created; their old entries may remain in the entity registry and can be deleted manually.
